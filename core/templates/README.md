# 模板使用说明（维护者参考）

本目录的模板用于帮助人快速补齐任务信息；它们不是 Codex 必须逐项读取或自动渲染的表单。日常任务可直接使用 [Prompt Compact Syntax](../prompt-compact-syntax.md) 的简写，模板用于需要更多提示或担心遗漏时参考。

## 先声明范围

会话首次任务中只要出现项目标记，Codex 就应识别本次范围；后续可省略，直到范围变化。为便于人阅读，可选地写成：

```text
范围：P0 + P1
```

范围、项目缩写和路径规则见 [`../../AGENTS.md`](../../AGENTS.md)。

项目标记不依赖固定分隔符：`P1 + P2`、`P1,P2`、`P1，P2`、`P1、P2`、`P1 P2`，或正文中分别出现 P1、P2，均表示本次涉及两者。`-` 或 `–` 表示连续范围，例如 `P0–P4`；可以混用为 `P0、P2-P4`。`范围：` 只是可选的可读性前缀。

## 字段分工

| 字段 | 用途 | 是否通常必填 |
| --- | --- | --- |
| `g` | 要解决的目标 | 是 |
| `b` | 背景与业务语境 | 已知背景不能从代码推断时填写 |
| `s` | 已知现状、症状或已有实现 | 缺陷、重构、架构任务通常填写 |
| `c` | 不可违反的约束与范围限制 | 有兼容性、数据、安全或范围限制时填写 |
| `r` | 最终要得到的结果 | 实施、设计和跨服务任务通常填写 |
| `i` | 影响服务、模块、接口或数据 | 是；决定读取和修改范围 |
| `p` | 本次如何执行：步骤、阅读顺序、实现偏好或输出节奏 | 需要指定过程时填写，不替代 `r` |
| `v` | 验证方式与验收证据 | 实施和缺陷修复任务通常填写 |
| `q` | 需要探索、核实或回答的问题 | `D` 可行性探索必填 |
| `d` | 已确认采用的方案或决策 | `P` 变更计划必填 |

`r` 说明“最终做成什么”，`p` 说明“本次怎么做”。

## 已提供模板的最小结构

| 类型 | 模板 | 最小必填 | 建议补充 | 按需填写 |
| --- | --- | --- | --- | --- |
| `F` 开发 | [feature.md](feature.md) | `g`、`i`、`r`、`v` | `c`、`s` | `b`、`p` |
| `B` 修复 | [bugfix.md](bugfix.md) | `g`、`s`、`v` | `i`、`c` | `b`、`r`、`p` |
| `R` 重构 | [refactor.md](refactor.md) | `g`、`s`、`r` | `c`、`i`、`v` | `b`、`p` |
| `A` 架构 | [architecture-design.md](architecture-design.md) | `g`、`s`、`r`、`c` | `i`、`p` | `b`、`v` |
| `X` 跨服务变更 | [cross-service-change.md](cross-service-change.md) | `g`、`i`、`s`、`c`、`r` | `p`、`v` | `b` |
| `C` 代码评审 | [code-review.md](code-review.md) | `g`、`s`、`i` | `c`、`v` | `b`、`r`、`p` |
| `D` 可行性探索 | [discovery.md](discovery.md) | `g`、`q`、`i`、`r` | `s`、`c`、`p` | `b`、`v` |

“最小必填”是推荐下限，不是机械校验。若任务说明已明确某项内容，不需要为了凑字段重复填写。

## 场景选择流程图

```text
收到一个任务
│
├─ 还不确定“能不能做、涉及什么、该选哪个方案”？
│  └─ D：可行性探索（只读调查、证据、方案对比；不改代码）
│       │
│       └─ 已选定方向，但还需明确改哪些文件、如何分步和怎么验证？
│          └─ P：变更计划（锁定边界与步骤；不改代码）
│              │
│              └─ 获得实施授权后，按任务性质进入 F / B / R / X
│
├─ 已有错误、异常、日志或可复现问题？
│  └─ B：缺陷修复
│
├─ 目标是新增或改变业务能力，且主要是正常功能实现？
│  └─ F：功能开发
│
├─ 外部行为基本不变，重点是改善结构、边界或可维护性？
│  └─ R：重构
│
├─ 需要评估架构选择、服务边界、数据所有权或技术取舍？
│  └─ A：架构设计/评审
│
├─ 影响多个项目、服务契约、消息链路或发布顺序？
│  └─ X：跨服务变更
│
└─ 已有代码变更，需要检查正确性、风险与测试？
   └─ C：代码评审
```

判断有交集时，优先按任务的**当前阶段**选择：不确定先用 `D`，方向已定但未实施用 `P`，进入实际改动再选 `F/B/R/X`。跨服务属性不妨碍使用 `B/F/R`；当本次核心交付是端到端契约、实施顺序或联调时，优先使用 `X`。

## 最小示例

```text
范围：P0 + P1
F
g: 增加巡检任务状态查询
i: P1
r: 提供按任务 ID 查询当前状态的接口
v: 单元测试和接口回归
```

需要规定过程时再加入 `p`：

```text
p: 先定位缓存键和已有状态入口；复用缓存；完成后补充测试
```

## 前置决策任务

`D` 用于可行性探索，只调查、核实和比较方案；`P` 用于已确认方向后的变更计划，只锁定范围和步骤。两者都不修改代码；实际实施由后续 `F/B/R/X` 任务完成。
