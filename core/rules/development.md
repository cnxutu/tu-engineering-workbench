# 公共 Codex 开发基准

适用于所有范围内服务中阅读、评审、设计或修改源码、配置、脚本、测试的任务。这是跨语言、跨仓库的默认开发基准，不承载产品事实、技术栈细则或固定命令。语言、框架、仓库和产品的专属约束由对应规则、目标目录的局部 `AGENTS.md` 与当前代码约定补充；指令优先级与事实可信度按 [`../AGENTS.md`](../../AGENTS.md) 分别判断，不能把当前代码误作高优先级指令。

## 生效与上下文

- P0 作为项目主仓库时，`ai-guidance/AGENTS.md` 是本会话的统一入口；其中的公共约束自动作用于用户指定的范围内仓库。服务仓库的局部 `AGENTS.md` 只补充本仓库特有的命令、技术规范和边界，无须反向引用或复制 P0 公共规则。
- 开始范围内仓库的工程任务时，在 P0 入口基础上读取目标目录的局部 `AGENTS.md`，再按条件读取规则加载最小必要的代码、契约、配置、产品知识和专项 Core。不得以文档推断代码现状，也不为“可能有用”而加载整个仓库或产品目录。
- 若会话并非从 P0 主仓库启动，则以该仓库自身的入口和局部约束为准；是否接入 P0 公共基准由该项目的工作区配置决定。
- 先判断任务类型：只调查或答复、边界清晰的局部改动、需要设计的功能/重构，或涉及公开契约与多个服务的变更。按类型选择相称的工作流、角色和验证，避免用重流程处理简单任务。
- 有适用的 Codex 平台 Skill 时先读取并遵循其 `SKILL.md`；没有 Skill 时采用等价的工程步骤。`core/skills/` 是本仓库工作流参考，不能覆盖平台、系统或开发者约束；与局部约束发生冲突时，按上述优先级处理。

## 先分析，再实施

- 实施前确认目标、范围、验收条件、非目标和不可变约束；查阅现有实现、调用方、局部约束、相关契约及可用验证方式，形成有证据的最小影响范围。关键事实缺失且不同解释会实质改变结果时，标明假设或阻塞并请求确认；不在此基础上直接实施高风险变更。
- 对新功能、行为变更、重构、架构或跨服务任务，若当前环境提供适用的 Codex `brainstorming` Skill，先读取并遵循；否则进行等价的简短分析，识别现状、影响范围、风险和方案。存在会导致兼容性、数据语义、服务边界、性能、安全或发布方式不同的多个实质可行方案时，给出不超过三个方案、取舍和推荐方案。
- 完成满足当前决策所需的最小分析后立即执行，不因可能继续探索而无限扩展调查范围。任务方向清晰时，以简短的“目标、影响、实施、验证”说明开始执行；不把分析固化成冗长设计文档、计划或清单，除非任务本身、局部约束或用户要求它们。
- 已读取的代码、配置、契约、测试和可复现命令结果才是事实；推断明确标为假设或待核实。发现范围外问题时记录其影响，不擅自混入当前改动。

## 确认机制

- 风险等级应依据受影响的公开契约、数据语义、权限、安全、生产或外部状态，以及操作的可逆性判断；文件数量、改动行数或一次工具调用涉及多个路径本身不构成高风险。
- 用户已明确目标、范围和实现方向，且改动可逆、符合下文风险分级验证中低风险定义时，直接执行必要的读取、编辑和本地验证；不要对连续小步骤重复确认。
- 仅在下列情况于实施前请求**一次**必要确认：存在会显著改变功能结果的多种解释或方案；会改变公开 API、消息契约、数据语义或服务边界；需要删除或覆盖数据、文件、历史；会影响生产、外部系统、权限、安全或产生额外费用；或所需权限、范围无法从现有信息确定。
- 确认时给出具体风险原因、受影响对象、推荐方案、备选方案与风险。获得决定后沿同一决策链执行，不重复询问；若发现会实质改变已确认功能结果、范围或风险等级的新事实，停止当前实施，说明变化并重新请求必要确认。提交、推送、发布及其他外部状态变更仍须有用户明确授权；用户未回复时，不执行待确认的高风险操作。
- 除非平台或系统层明确禁止，高风险判断成立时不得直接终止而不向用户说明原因并请求决策。若工具调用被平台自动审核拒绝，应明确标注为平台限制，不将其表述为用户拒绝或任务完成，并提供缩小范围、分步执行或等待授权等可行下一步。

## 方案与实现

- 以满足当前已确认需求的最小改动为准，遵循 KISS 与 YAGNI；除非当前需求、已验证调用方或已确认契约证明必要性，不为未确认的未来场景预留抽象、配置、兼容分支或扩展点。
- 优先复用项目现有能力、框架与依赖；确无合适能力时再评估成熟依赖，最后才新增自定义实现。评估成熟依赖时考虑维护状态、许可证、安全风险、与现有技术栈的兼容性及引入成本；新增依赖或基础设施须说明必要性、影响与替代方案。
- 不新增单次使用的通用层、样板工具或猜测性的辅助函数；优先使用项目既有工具、成熟库和语义恰当的数据结构。不要为不可能或未经证实的场景加入隐式纠偏、兼容、归一化或兜底逻辑。
- 每项改动都应能追溯到任务目标。保持现有代码风格、模块边界和公开契约；变更 API、消息、数据结构或配置默认值前，确认兼容性、迁移、回滚和调用方影响。
- 不静默吞掉异常或以日志替代错误处理；按项目既有约定表达预期失败，保留排查所需的根因和上下文，且不泄露敏感信息。重试、降级、补偿或返回默认值等恢复行为必须有明确业务语义或既有约定，不为未经证实的场景擅自添加。

## 调试与验证

- 遇到缺陷、异常或验证失败，先复现并收集调用链、日志、配置、版本或测试证据，再定位最小根因；不要连续尝试猜测性修补，也不要通过弱化断言、跳过测试或吞掉异常来制造“通过”。无法安全或稳定复现时，记录最小可观察症状、已有证据、证据缺口与下一步取证方式，不以猜测性修补替代根因定位。
- 执行改动前，若存在可快速运行的受影响测试、静态检查或复现命令，先记录其结果；既有失败不得表述为本次改动导致，也不得通过跳过测试掩盖。基线命令不可用、耗时过长或依赖不可获得时，说明原因和未覆盖范围，并选择风险相称的替代验证。
- 新增或修复行为时，提供与风险相称、可重复的自动化验证：修复优先覆盖原问题的回归路径，行为变更覆盖正常路径和关键失败路径；跨边界变更验证契约和兼容性。

### 风险分级验证

- 同一任务命中多个等级时，按最高适用等级执行全部验证要求；风险无法可靠判断时，先按中风险处理，并在可能触及高风险边界前确认。
- 低风险：局部、可逆，且不改变公开契约或数据语义。至少执行受影响的单元测试或静态检查，并复查差异。
- 中风险：改变业务行为、配置默认值、跨模块调用或关键失败路径。除低风险要求外，覆盖正常路径和关键失败路径，并说明兼容性影响。
- 高风险：改变公开 API、消息契约、数据迁移、权限、安全、跨服务链路或生产行为。除中风险要求外，说明调用方影响、发布与回滚方式，并执行契约、集成或端到端验证；无法执行时明确未覆盖范围与残余风险。
- 涉及数据迁移或修复时，额外说明数据校验方式、幂等性、失败恢复与回滚边界。

## 完成与交接

- 完成前复查差异，确认没有无关格式化、重构、产物、敏感信息或意外配置变更；执行受影响的测试、静态检查或构建。无法执行时如实说明原因、未覆盖范围和残余风险，不把未执行的验证说成已通过。
- 交接至少说明改动目标与范围、关键兼容性或设计决定、已执行验证及结果、未验证项与残余风险；用户要求或仓库流程需要时，再进入提交、评审或发布步骤。

## 变更纪律与安全

- 只修改任务必需的文件和行；不顺带重构、格式化、删除或修复无关问题。保留他人已有改动，并只清理由本次改动造成的无用代码。
- 不读取、记录、输出或提交密钥、Token、凭据、个人数据、生产 payload 或其他敏感运行信息；日志、测试样例和文档使用脱敏内容。意外发现敏感信息时，不复制到对话、代码、日志或提交记录，最小化暴露范围，并提示用户按既有安全流程处置。
- 不使用破坏性命令、覆盖历史或批量删除来“清理”工作区；在可能影响数据、环境或他人改动的操作前，核对目标与授权。删除、覆盖、移动或批量操作前，核对解析后的绝对目标路径、受影响对象和任务授权；目标超出任务范围时停止并请求确认。
