# Prompt Compact Syntax（人机任务协议）

这是 P0 中用户与 Codex 的默认任务描述约定。它取代长 Markdown 模板作为日常任务入口。用户用一个**大写任务类型**和若干**小写上下文字段**描述任务；Codex 将其展开为完整的分析、设计、实施或评审工作流。

## 语法

第一行是单个大写任务类型；后续每行使用 `小写字段: 内容`。

```text
F
g: 新增机场设备能力
b: 新设备需要接入巡检平台
s: P1 已有设备管理和指令入口，P2–P4 尚未支持该协议
c: 保持既有 DJI 链路兼容；不得改变普通 OSD 与 DRC OSD 的缓存语义
r: 支持设备注册、OSD 上报和控制指令下发
i: P1、P2、P3、P4
p: 先核实 P1–P4 现有链路；明确契约与发布顺序后再实施
v: 单元测试、模拟 MQTT 上下行和现有 DJI 链路回归
```

字段内容可以跨行续写；续行应缩进。大小写有语义：`B` 是任务类型 Bugfix，`b` 是背景 Background。

## 大写任务类型

| 标记 | 英文含义 | Codex 默认工作重点 |
| --- | --- | --- |
| `F` | Feature | 澄清需求、定位代码、设计并实现功能、验证回归。 |
| `B` | Bugfix | 复现/定位根因、提出最小修复、验证并防回归。 |
| `R` | Refactor | 识别耦合与风险，保持外部行为兼容地演进。 |
| `A` | Architecture | 评估架构/技术方案，明确边界、契约、取舍、发布与回滚。 |
| `X` | Cross-service Change | 分析 P1–P4 的端到端影响、契约、实施顺序与联调。 |
| `C` | Code Review | 按正确性、兼容性、性能、安全、可维护性和测试充分性评审。 |
| `D` | Discovery / Feasibility | 只调查、核实和比较方案，输出可行性结论；不修改代码。 |
| `P` | Planning / Change Plan | 基于已确认方向锁定修改边界和计划；不直接实施。 |

## 小写上下文字段

| 标记 | 英文含义 | 中文说明 |
| --- | --- | --- |
| `g` | Goal | 目标。 |
| `b` | Background | 背景。 |
| `s` | State | 当前状态。 |
| `c` | Constraints | 约束与不可修改范围。 |
| `r` | Result | 期望结果。 |
| `i` | Impact | 影响范围：服务、模块、接口、消息、数据或配置。 |
| `p` | Plan | 实施要求、执行步骤、输出节奏或实现偏好；不等同于最终结果。 |
| `v` | Verification | 验证方式与验收证据。 |
| `q` | Questions | 需要探索、核实或回答的问题；用于 `D`。 |
| `d` | Decision | 已确认的方案或决策；用于 `P`。 |

## Codex 解析规则

1. 看到该格式时，先根据大写类型选择最小必要的 Core 角色、规则和 Skill，再根据 `i`、`b`、`s` 定位产品知识和源码。
2. 字段未提供不代表没有约束。Codex 只能从已读取的产品知识与代码补充**已验证事实**；其余内容要列为待确认，不能臆造。
3. `X` 或 `i` 涉及多个仓库时，先读取 `workspace.yaml`、产品入口及相关 Flow/契约，再按路径核实目标代码。
4. `r` 描述要达成的结果，`p` 描述本次如何执行；`c`、`r`、`v` 是任务的直接验收依据。若相互冲突，以用户最新明确说明为准，并指出冲突。
5. 该简写协议不覆盖仓库局部约束。发生冲突时：**用户最新明确要求与当前代码/仓库局部约束 > 产品上下文 > Core 通用规则**。
6. `D` 必须保持只读探索，输出证据、方案对比、风险、待核实项和推荐下一步；`P` 必须保持只读计划，输出范围、代码入口、实施顺序、风险与验证。除非用户在后续任务明确转换为 `F/B/R/X`，不得实施代码改动。

## 与旧模板的关系

`core/templates/` 中的文件保留为历史参考与需要长篇任务文档时的输出框架，但不再是日常 Prompt 的默认入口。除非用户显式点名某个模板，Codex 应优先按本协议理解任务，不要求用户填写 Markdown 模板。
