# 设备接入核心上下行对接任务清单

> 用于每个新厂商、新型号或新驾驶舱设计能力接入前后的任务拆解与验收。目标是确保至少一个核心能力形成“设备上报可见、用户控制可达、执行结果可回读”的闭环。

## 使用方式

在方案评审时建立本清单，并为每项记录责任边界、产物链接和证据。推荐状态为 `not_started`、`in_progress`、`pending_verification`、`verified`、`not_applicable`；未知项不能以推测标为 `verified`。

这不是完整项目计划，也不替代厂商协议、TSL 或测试用例。它只覆盖一条核心上下行链路的必要门槛；媒体、任务编排、算法等其他能力需按自身链路补充。

## 0. 先把新设计切成可验收能力

面对原型或新交互，不要直接按页面按钮新增接口。先为每个候选能力明确以下问题：

| 要确认的内容 | 应产出的结论 |
| --- | --- |
| 页面是展示状态、一次动作、连续遥控、配置，还是高风险操作？ | 交互类型、权限级别和是否需要执行回读 |
| 用户看见的状态来自设备、平台计算，还是两者组合？ | 唯一状态来源及刷新方式（REST、WebSocket 或轮询） |
| 设备是否已有协议能力？ | 厂商 APDU/Topic/服务字段与版本依据；没有则记录协议缺口 |
| 什么才算成功？ | “平台已受理”和“设备已执行”的分别判据 |
| 首个闭环最小范围是什么？ | 一个设备、一个状态入口、一个控制入口、一个可观测回读 |

没有这些结论时，接口名、枚举和前端文案都不应被当作最终契约。

## 1. 身份、语义与边界

- [ ] 固定厂商、型号、固件/协议版本和协议来源；将本次能力明确到协议消息或服务项。
- [ ] 列出设备身份转换：厂商 SN/会话标识、`productKey`、`deviceName`、项目归属和 `iotGatewayId` 分别由谁生成、校验和持久化。
- [ ] 区分状态、在线性、故障、告警、控制权和命令执行反馈；不得用一个字段代替另一种语义。
- [ ] 明确 P4-1、P3、P2、P1、前端各自的唯一职责，避免 P1 解析厂商协议或适配器拼装业务快照。
- [ ] 写明失联、重连、重复消息、乱序消息和未知枚举值的预期处理；未知值应保留可排查信息而不是静默改写。

## 2. 固化稳定契约

- [ ] 建立字段映射表：厂商字段、下划线/驼峰转换、物模型 `identifier`、数据类型、单位、枚举和值域、是否增量、缺省语义。
- [ ] 在 P2 确认产品、TSL 属性/事件/服务以及服务参数；TSL 标识是跨层契约，改动须评估所有消费者。
- [ ] 为上行消息指定业务投递方式（例如 Data Rule）和目标消息契约；记录生产端、消费者、错误策略和幂等键。
- [ ] 为下行命令指定服务标识、参数、超时、是否连续输入、是否需要控制权及停止/撤销语义。
- [ ] P1 定义强类型 DTO、状态快照和接口响应语义；将“已受理”与“已执行”分开建模和展示。
- [ ] 为前端确定 REST 初始读、WebSocket 增量推送或轮询的组合；协议枚举说明应引用最终协议/TSL 证据，而非页面猜测。

## 3. 上行链路验收

- [ ] P4-1 对正常帧、非法帧和未知字段有解码与映射测试，标准消息携带可路由的设备身份和 `identifier`。
- [ ] P3 已确认协议实例、Custom Adapter/Jar 或传统 Codec 的选择、启用配置和实际路由目标。
- [ ] P2 能接收对应物模型消息；若需要业务消费，Data Rule 的过滤条件、目标和投递结果有可复核证据。
- [ ] P1 消费端能校验并转换该消息，状态类数据按增量/全量语义正确合并，事件类数据不被误作状态覆盖。
- [ ] 驾驶舱能获取初始状态并在变化后更新；验证同项目/跨项目可见性符合权限和会话隔离设计。
- [ ] 现场至少验证一次正常上报、一次重连后上报和一次未知/不完整输入的可观测处理。

## 4. 下行链路验收

- [ ] 从前端触发点到 P1 的用户、项目、设备归属和操作权限全部校验；高风险命令有额外安全约束。
- [ ] P1 将业务命令转换为 P2 服务调用，而不是向适配器直接发送厂商载荷。
- [ ] P2 已校验服务标识与参数，并能将 `thing.service.invoke` 路由至目标网关和设备。
- [ ] P3 与 P4-1 能接收目标服务，编码为预期厂商命令；无会话、编码失败和不可支持服务均有明确错误路径。
- [ ] 前端和接口文档准确声明同步响应含义：受理、排队、发送失败或设备已执行；不得把异步发送成功写成设备执行成功。
- [ ] 设备执行后的状态、通知或厂商回执能够重新进入上行链路，形成闭环；紧急停止和连续遥控要验证停止条件与失联处置。

## 5. 发布、观测与回滚

- [ ] 列出部署依赖：P2 产品/TSL/Data Rule、P1 消费与控制代码、P4-1 包、P3 实例/路由配置和前端版本；安排不会产生未知消息或无消费者窗口的启用顺序。
- [ ] 为每层指定不含敏感数据的观察点：设备身份、消息标识、路由结果、业务事件 ID、命令受理结果和状态版本/时间。
- [ ] 将适配器映射、TSL、Data Rule、P1 DTO/接口和前端枚举纳入同一份变更评审，防止单层发布造成契约漂移。
- [ ] 预先演练或写明回滚动作：停止下行入口、撤回路由/适配器、暂停 Data Rule、恢复兼容 TSL 的顺序与影响。
- [ ] 核对告警、命令失败、未知枚举、无会话和消息积压的排查入口与责任人。
- [ ] 将实机联调记录、测试结果和未完成项写入交付证据；现场未验证的项目必须保持 `pending_verification`。

## 闭环完成判据

一个核心能力只有同时满足以下条件，才可标记为完成：

1. 对应协议/服务和 P2 物模型契约已固化，并有映射证据。
2. 设备侧上行能在驾驶舱获得正确、可解释的状态或事件。
3. 驾驶舱操作能通过 P1 → P2 → P3 → P4-1 到达设备侧。
4. 设备实际执行与否能由回读状态、通知或厂商回执确认，而非仅依赖同步 HTTP 响应。
5. 发布观察点、异常路径和回滚方案均已确认。
