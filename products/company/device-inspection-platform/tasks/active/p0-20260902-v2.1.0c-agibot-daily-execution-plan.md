## 1. 结论与今日完成定义

建议采用“后端先行、前端紧随状态闭环”的节奏，而不是等所有后端控制、视频和告警都完成后才开始前端。原因是监控列表、详情和 WS 的可开发输入依赖真实的设备身份、状态字段、增量规则和 P2 投递样本；但前端页面字段、刷新和错误态可以在**状态快照可查询且样本可复放**后立即细化。

今天的最小成功结果不是“机器狗功能完成”，而是以下两项：

1. 后端形成可追溯的最小契约包，允许 P1 开始状态链路实施；未决项必须明确为阻塞项，不能靠默认值绕过。
2. 若门禁全部通过，则开始并优先完成 P1 状态垂直切片 `B-01 → B-02 → B-03`；若尚未通过，完成样本校验与 P1 实施准备，不承诺写入业务代码。

前端详细评审的启动条件是：`B-03` 已能对一台脱敏测试设备保存可查询状态快照，或至少已有可被 P1 自动测试复放的状态样本和冻结字段表。届时只细化状态相关页面，不预先冻结控制、视频等仍缺外部契约的接口。

## 7. B1 可行性结论与实施边界（不含本轮代码）

`B1` 可实施，且应只完成“机器狗分类能够成为 P1 可投影、可绑定并纳入监控刷新范围的设备”。机器狗监控卡片查询与业务状态属于紧随其后的独立任务；本项不包含机器狗状态缓存、详情、位置、告警、控制、任务或视频。

| 改动域 | 计划改动 | 现状依据 |
|---|---|---|
| 分类映射 | 激活 `DictMonitorDeviceCategoryEnum.ROBOT_DOG`，配置 `p2CategoryCode = "UGV"`，并补字典映射测试。 | 当前枚举已预留但被注释；P1 的实时投影、启动导入和日终对账均用此枚举决定设备是否可投影。 |
| 实时投影与概览刷新 | 让 `DeviceProjectionRealtimeSyncService`、`DeviceProjectionSyncTask` 将已绑定空间的 `UGV` 视为监控设备，以便创建、更新、删除/迁出时触发既有监控概览刷新。 | 两处 `isMonitorProjection` 当前只包含 `APT/UAV/CAM`；仅激活枚举时设备会投影，但监控刷新事件不会覆盖机器狗。 |
| 初始存量设备 | 在发布前确定存量 `UGV` 的投影回填方式：复放一次 P2 更新事件，或提供受控的一次性投影导入入口。 | P1 日终同步对不存在的本地投影只记录 `P1_MISSING`，不会创建；`DeviceProjectionBootstrapService` 已有导入能力但当前未发现调用入口。 |
| 后续监控可见性 | 在 B1 验证投影与空间绑定后，再单独实现机器狗列表 SQL/卡片和业务状态 Resolver。 | `MonitorDeviceServiceImpl` 与 `IDeviceMonitorMapper.xml` 当前只查询 `APT/UAV/CAM`；不能把 `UGV` 当作无人机子设备或复用无人机状态规则。 |

**B1 验收：** `AGC/UGV` 的 P2 设备经实时事件或受控回填后进入 P1 `manage_device` 投影；绑定空间后仍保持 P2 原始分类码 `UGV`；分类映射、创建/更新/删除或迁出、以及原有 `APT/UAV/CAM` 回归均有自动测试。真实联调另以 P2 实际生成的设备主数据验证。
