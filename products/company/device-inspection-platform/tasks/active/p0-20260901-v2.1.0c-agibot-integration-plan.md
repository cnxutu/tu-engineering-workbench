# 巡检平台 2.1.0.c 智元机器人接入开发规划书

> 任务类型：P（Planning / Change Plan）  
> 版本：2.1.0.c  
> 规划日期：2026-09-01（周二）  
> 状态：active  
> 适用范围：`c-drone-inspection`、`c-iot-server`、`c-iot-gateway`、适配器仓库及前端联调  
> 本文性质：执行基线与工作量留痕；不是对当前代码已具备能力的承诺。

## 1. 先给结论

本版本不按“4 天把机器狗全部接入并完成所有业务适配”作为可接受承诺。建议先冻结一个可验收的 **MVP 垂直切片**，再按能力批次扩展：

| 批次 | 目标 | 建议投入 | 发布门槛 |
|---|---|---:|---|
| M0 | 需求、协议、物模型、接口和联调样本冻结 | 0.5–1 人日（全员工作坊） | 目标型号/SDK/身份/identifier/成功语义有书面结论 |
| M1 MVP | 单台测试机器人完成设备注册/在线、基础状态、故障、最小控制命令的 P2→P1→P3→适配器→设备闭环 | 8–12 人日（两后端并行，未含厂商阻塞） | 上下行链路、失败路径、日志和回滚均可复现 |
| M2 业务整合 | 监控列表/详情、控制面板、任务或航线、媒体入口、权限和审计按原型逐项适配 | 10–18 人日 | 前后端接口与交互验收通过 |
| M3 扩展能力 | 运动/姿态/传感器/视频/高级任务、性能和多机并发 | 8–20+ 人日 | 以厂商能力和现场网络为前提单独排期 |

在 M0 结论完成前，任何“剩余 X 天全量完成”的估算都标为 `pending_verification`，不作为个人交付承诺。

## 2. 范围、非目标与成功标准

### 2.1 本次范围

- 将智元机器人作为独立厂商/型号接入巡检平台，不把 DJI Topic、DJI Codec 或云深处 M20 Pro 协议当作默认复用前提。
- 复核设备主数据：厂商、型号、设备类型、模型编码、设备 SN/平台身份、网关归属和展示字段。
- 定义并落地最小统一物模型：运行态、基础状态、故障事件、控制权/急停和至少一条可验证控制服务。
- 打通上行：机器人/SDK → 适配器或 Bridge → `c-iot-gateway` → `c-iot-server` → RocketMQ/Data Rule → `c-drone-inspection` → 前端展示/推送。
- 打通下行：P1 业务入口 → P2 `invokeDeviceService` → P3 协议实例/Codec → 适配器或 Bridge → 机器人，并区分“发送/受理/执行完成”。
- 按原型核对已有页面和接口的复用边界，补齐机器狗专用分支、字段、权限、错误提示和空态。
- 形成可回滚发布包、联调清单、每日工作记录和变更单。

### 2.2 明确非目标

- 不在本规划阶段承诺所有智元型号、所有 SDK 能力、所有传感器/ROS2 Topic 或全部视频能力。
- 不把 P1 的业务 Handler、前端 DTO 或 WebSocket 字段直接当作 P2 TSL；三者必须分别核对。
- 不在适配器中编排控制权、重试、任务状态机、权限或业务数据库。
- 不修改现有 DJI 或其他已接入设备链路，除非联调证据证明公共层缺陷且另行登记变更。
- 不在未知设备型号、SDK 版本、通信方式和生产配置未确认时合并或发布。

### 2.3 成功标准

以一台脱敏测试设备和固定软件版本完成以下可重复证据：

1. 设备可创建/绑定，身份可从机器人侧稳定映射到平台设备。
2. 连接、断开、重连和状态超时的 ONLINE/OFFLINE 语义符合书面阈值。
3. 基础状态属性和故障事件经 P2 Data Rule 投递，P1 正确路由并更新页面/缓存/WebSocket。
4. 最小控制命令经过权限校验、P2 服务模型校验、P3 路由和适配器发送；返回值明确是发送成功、设备受理、执行完成或失败。
5. 急停/控制权丢失不会被平台重试抵消，且有审计记录。
6. 关键失败路径可观测、可定位；回滚后旧 DJI/其他设备链路不受影响。

## 3. 当前已验证事实与待确认项

### 3.1 已验证事实（来自当前代码/维护文档）

| 事实 | 证据 |
|---|---|
| P1 的跨服务上行统一经过 `InspectionIotUpstreamConsumer` → Converter → Router → identifier Handler；未知 identifier 会确认消费，不会自动兼容。 | `ai-guidance/products/company/device-inspection-platform/repositories/c-drone-inspection/key-entry-points.md`、P1 当前代码入口 |
| P1 的控制/任务/DRC 应通过 `InspectionIotCommandGateway` 出站，不应在 Controller 直接拼协议。 | 同上 |
| P2 `IoTDeviceRpcApi#invokeDeviceService` 会校验产品服务物模型并构造 `thing.service.invoke`；下行按设备网关归属投递 P3。 | `repositories/c-iot-server/device-thing-model-tsl.md`、P2 当前代码 |
| P2 上行设备处理、Data Rule 和 RocketMQ 投递是独立路径；Data Rule 需按 method/identifier 匹配。 | `repositories/c-iot-server/message-bridge-and-data-rule.md` |
| P3 通过协议实例的 `protocolCodecId` 选择唯一 Codec；也存在 `CustomProtocolAdapter` 路径，网关本身无设备业务数据库。 | `repositories/c-iot-gateway/protocol-instance-and-codec-selection.md`、`gateway-upstream-downstream-bridge.md` |

| P1 已有统一 IoT 上行消费、identifier 路由、设备状态/告警/媒体/任务等 Handler，以及 `InspectionIotCommandGateway` 下行门面；现有统一 identifier 集中在 `InspectionIotIdentifiers`。 | P1 `b-inspection-platform-iot/.../InspectionIotUpstreamConsumer.java`、`InspectionIotMessageRouter.java`、`b-inspection-platform-common/.../InspectionIotIdentifiers.java`、`b-inspection-platform-core/.../InspectionIotCommandGatewayImpl.java` |
| 监控请求已预留 `ROBOT_DOG` 展示分类，但代码注释明确当前暂无机器狗列表数据；这不是“机器狗页面已完成”的证据。 | P1 `MonitorDeviceV2ListReq.java`、`DictMonitorDeviceCategoryEnum.java` |
| P1 的设计文档明确目标是业务只消费统一物模型，不建立按 `dji`/`robotDog` 划分的业务数据交互模块；因此智元优先评估扩展统一 IoT 契约和 Handler，而不是复制一套厂商协议业务模块。 | P1 `docs/巡检对接iot改造方案.md` |

## 5. 端到端目标链路（待 M0 以实际方案替换）

### 5.1 上行

```text
智元机器人/SDK 回调
  →（适配器或原生 Bridge：设备身份、连接、状态、故障、传感器）
  → c-iot-gateway：协议实例/CustomProtocolAdapter、标准 UpstreamDecodedData
  → c-iot-server：设备查询、运行态、属性/事件处理、Data Rule
  → RocketMQ Topic/Tag
  → c-drone-inspection：InspectionIotUpstreamConsumer → Converter → identifier Handler
  → Redis/业务库/WebSocket/前端
```

### 5.2 下行

```text
P1 HTTP/任务入口
  → 业务路由与权限/控制权校验
  → InspectionIotCommandGateway
  → P2 IoTDeviceRpcApi#invokeDeviceService（服务 TSL 校验）
  → P3 网关下行 Topic、协议实例与 Codec
  → 适配器/Bridge → 智元 SDK → 机器人
  → ACK/状态变化/失败回传（完成语义必须单独定义）
```

若采用独立 C++ Bridge，Bridge 生命周期、认证、心跳、幂等、背压、断线重连、消息格式和版本回滚必须作为 M1 的发布依赖；不能把 Bridge 当作 P3 classpath 中的普通 Maven Adapter。

| 下周一 D4 | 回归、回滚、前端 MVP 验收和范围复盘 | 决定进入 M2，或冻结为 M1 版本 |

D3/D4 仍未具备厂商 SDK、设备或环境时，结论应写成“平台桩闭环完成、实机闭环阻塞”，不得改写成“机器狗已全部接入”。

## 10. 接口与消息契约冻结模板

不在规划书中擅自发明最终 identifier；以下是今天要填写的模板。

| 层 | 字段 | 必须明确 |
|---|---|---|
| 设备身份 | `productKey`、`deviceName`、设备 SN、P1 `deviceSn`、网关 ID | 来源、唯一性、替换/迁移 |
| 上行外层 | `method`、messageId/requestId、时间戳、设备上下文 | 生成方、幂等键、时序 |
| 上行模型 | property/event `identifier`、payload 字段 | 类型、单位、枚举、空值、频率 |
| 下行外层 | `thing.service.invoke`、目标设备、`identifier`、`params` | P1 调用 DTO 与 P2 校验一致 |
| 回复 | ACK/受理/完成/失败、错误码、超时 | 同步/异步、重试、前端文案 |
| 状态 | SDK 连接、平台在线、业务状态、控制权 | 不同语义不可合并 |
| 安全 | 急停、恢复、人工接管 | 权限、审计、禁止自动重试 |

契约变更必须同时更新 P1 Handler、P2 TSL/Data Rule、P3/适配器映射、前端字段和测试；只改一端视为未完成。

## 11. 验收矩阵

### 11.1 功能验收

| 场景 | 预期 | 证据 |
|---|---|---|
| 首次连接/注册 | 平台身份可查询，网关归属正确 | P2/P3 日志与设备查询 |
| 正常上报 | P2 处理，Data Rule 投递，P1 Handler 更新展示 | MQ 消息 + P1 快照/WS |
| 故障上报/恢复 | 事件不被当作普通在线状态，恢复语义明确 | 故障码、事件和页面状态 |
| 断线/重连 | 平台在线按阈值变化，重连后恢复且不重复刷屏 | 时间线与状态事件 |
| 最小控制 | 权限通过后发送；设备 ACK/受理与完成分开 | API 响应、适配器回调 |
| 急停/控制权抢占 | 急停独立、不可被普通重试抵消；人工接管可见 | 安全用例、审计记录 |
| 未知 identifier | P2/P1 明确失败或确认消费策略符合设计 | 错误日志、MQ 消费结果 |
| 旧设备回归 | DJI 及其他已接入设备用例不受影响 | 受影响模块回归结果 |

### 11.2 非功能验收

- 断线重连、重复消息、乱序、迟到消息和超时可定位。
- 高频数据有采样/限流/丢弃策略，不能把 SDK 回调线程阻塞在网络或数据库操作上。
- 日志只记录脱敏的设备标识、requestId/messageId 和错误上下文，不记录凭据或生产 payload。
- 发布顺序和回滚顺序已演练：先兼容模型/消费者，再启用新适配器和规则；回滚同时恢复 TSL、Data Rule、P1 Handler、P3 配置和适配器/Bridge 版本。

## 12. 发布、回滚与变更控制

### 12.1 推荐发布顺序

1. 合并并发布兼容的 P1 Handler/DTO（未知 identifier 仍按既有策略处理）。
2. 导入未发布产品 TSL，校验 Data Rule 引用；记录版本号和导入结果。
3. 发布 P2 Data Rule/运行态配置。
4. 发布 P3 协议实例和适配器/Bridge，先关闭新设备流量。
5. 测试设备灰度启用，完成 M1 验收后再扩大范围。

### 12.2 回滚触发条件

- 实机连接或重连不稳定，导致在线状态抖动。
- 急停、控制权或失败语义无法证明安全。
- 新消息大量进入未知 identifier、DLQ 或阻塞现有消费组。
- P1 页面/任务状态与 P2 运行态出现不可解释的跨服务不一致。

### 12.3 变更单最小字段

`变更编号`、`原范围`、`新范围`、`原因/证据`、`受影响契约`、`新增人日`、`负责人`、`验收变化`、`回滚方式`、`批准人`、`日期`。任何新增页面、服务、字段、传感器或型号都先入变更单，再更新排期。

### 14.2 主要风险

1. **型号/SDK 不确定**：D1 Max 资料不能套用到其他智元型号；未锁定版本前不估算适配器完成时间。
