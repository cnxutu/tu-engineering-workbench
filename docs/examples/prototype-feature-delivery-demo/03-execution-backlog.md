## EXT-01：取得下行与状态回读样本

- 目标：证明最终 service、command、参数和设备状态回读字段可形成闭环。
- 前置：`G2_contract_confirmed=verified`。
- 需要用户取得：
  1. 一条脱敏下行请求及 P2 受理结果。
  2. 前灯打开和关闭后的状态上报各一条。
  3. 设备无会话或拒绝命令的错误样本。
- 预期：`DEV-02` 不再依赖模拟 command 或猜测错误语义。
- 验收：样本能映射到 `requestId/light/enabled`，并证明设备完成由状态回读而非同步 HTTP 表达。
- 模拟结果：尚未取得，保持 `blocked`。

## DEV-01：实现 REST 边界、DTO、权限与占用校验

- 能力：CAP-03、CAP-04。
- 上下文入口：`02-api-contract.md`；目标仓库的 Controller、DTO、数据权限、设备上下文与异常处理同类实现。
- 范围：新增补光动作 Controller 方法、请求/响应模型、Bean Validation、Swagger/OpenAPI、项目/设备/权限/占用校验。
- 非目标：IoT 真实 service 参数、设备回执、重试、数据库表、独立 WS。
- 步骤：
  1. 核实同类 Controller 路由、响应信封、权限和异常约定。
  2. 创建或扩展请求/响应模型，保持文档与校验一致。
  3. 校验当前项目、机器狗设备、用户控制权限和外部占用。
  4. 调用尚未落地的业务服务边界；若仓库不允许安全拆分，则与 DEV-02 合并，不创建伪成功实现。
  5. 增加正常、字段非法、无权限、设备不可见和占用冲突测试。
- 预期：REST 边界可编译、契约可生成，任何未实现路径都不会返回假 `ACCEPTED`。
- 验收：相关测试通过；生成 OpenAPI 与 Step 2 的 method/path/schema 一致。
- 模拟执行结果：未实际执行，状态 `ready`。

## DEV-02：实现 IoT 补光命令调用

- 能力：CAP-03、CAP-05。
- 上下文入口：Step 2 上游契约、EXT-01 样本、目标仓库现有 IoT 命令网关与测试。
- 前置：EXT-01、DEV-01 verified。
- 范围：业务命令到 P2 service 请求的转换、受理/拒绝映射、请求追踪。
- 非目标：自动重试、设备完成状态机、修改 P2/P3/适配器。
- 步骤：核实并复用现有网关；映射字段；区分受理与执行；覆盖无会话、拒绝和异常。
- 预期：P1 能发送冻结的补光命令，只在上游受理后返回 `ACCEPTED`。
- 验收：单元测试验证请求映射、权限不绕过、拒绝不伪装成功；脱敏样本可重放或等价验证。
- 模拟执行结果：等待 EXT-01，状态 `blocked`。

## DEV-03：验证状态回读与 OpenAPI 契约

- 能力：CAP-01、CAP-02、CAP-05。
- 前置：DEV-01、DEV-02 verified。
- 范围：验证既有快照 REST/WS 能回显三灯状态；对比运行时 OpenAPI 与批准契约。
- 非目标：新增补光查询/WS、改变完整快照合并规则。
- 预期：命令和状态读取形成可测试的业务闭环；契约无静默漂移。
- 验收：开启/关闭三灯的状态字段均有自动测试；首屏与 WS 使用同一 DTO；OpenAPI 差异已清零或有批准决策。
- 模拟执行结果：状态 `blocked`。

## INT-01：前端联调

- 场景：首屏、三灯切换、外部占用、请求拒绝、WS 断线重连。
- 验收：前端不把 `ACCEPTED` 显示为设备执行成功；重连后 REST 状态能覆盖本地临时状态。
- 证据：脱敏请求/响应、页面录屏或截图、WS 事件摘要。
- 模拟执行结果：状态 `blocked`。

## INT-02：设备闭环联调

- 场景：P1 请求 → P2 受理 → P3/适配器发送 → 设备变化 → 状态上报 → P1 快照 → 前端回显。
- 验收：至少覆盖一次开启、一次关闭、一次无会话拒绝；每一跳有可复核的脱敏关联标识。
- 证据：各层观察点摘要，禁止复制生产 payload 或凭据。
- 模拟执行结果：状态 `blocked`。
