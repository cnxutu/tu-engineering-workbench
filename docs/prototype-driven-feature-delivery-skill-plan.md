# 原型驱动功能交付 Skill 流程化方案

> 状态：proposal，待评审后实施  
> 日期：2026-09-03  
> 范围：P0 `ai-guidance-workflows` 的流程与 Skill 规划；本文件不授权修改业务代码或对外发布接口。  
> 经验来源：智元机器狗接入的 active task、端到端链路、设备接入清单，以及现有 `tu-scaffolding-spring-feature-from-prototype`。

完整模拟案例见 [机器狗补光控制：四阶段操作剧本](examples/prototype-feature-delivery-demo/walkthrough.md)。案例包含可直接查看的 `task.yaml`、四阶段产物和 OpenAPI 草案；其中接口和业务决定均为流程演示，不代表真实需求已确认。

## 1. 结论

建议保留“影响范围 → 接口契约 → 任务实施 → 联调提测”四阶段，但不要拆成四个互相独立、各自猜测上下文的 Skill。应将现有 `tu-scaffolding-spring-feature-from-prototype` 升级为一个**有阶段门禁、可断点续跑、以 P0 任务包为状态载体**的生命周期 Skill。

核心方案：

1. 一个 Skill 负责识别当前阶段、检查前置产物并路由工作；用户仍可显式指定只执行某一阶段或某几个任务。
2. 每个功能在 P0 只维护一个任务包，四阶段各有单一权威产物，阶段间通过稳定编号和链接传递结论，不靠聊天历史恢复状态。
3. Step 1 只做证据化影响分析和对齐问题，不提前把猜测写成最终接口。
4. Step 2 以独立契约文件完成评审；是否同步生成 Controller/DTO 骨架由目标仓库现有模式决定，不把“生成空 Controller”设为所有项目的强制动作。
5. Step 3 将外部确认任务、可执行代码任务和联调任务分开，并要求每个任务具备前置、上下文、步骤、预期、验收、证据和回填状态。
6. Step 4 用契约和任务验收项驱动联调、缺陷修复与提测，不把 HTTP 成功、平台受理、消息投递和设备执行混为一种成功。

## 2. 从机器狗 tasks 得到的经验

### 2.1 已经验证有效的做法

现有机器狗材料已经具备目标流程的大部分要素：

- 前端接口台账按“已有可复用、已有需改、全新、待确认、本期不做”分类，能避免按页面按钮直接新增接口。
- 后端与适配器对接方案把页面能力追到 P1、P2、P3、P4-1 的责任边界、消息标识和数据来源。
- execution backlog 将需要本人协调的 A 类事项与可由 AI 实施的 B 类代码任务分开，并设置实施门禁。
- daily execution plan 对已执行任务补充了测试数量、结果、未联调边界和下一步。
- 端到端链路明确区分“平台已受理”和“设备已执行”，并要求状态、通知或设备回执形成闭环。

这些内容应成为通用 Skill 的内置方法，而不是每次重新靠提示词要求 AI 想起。

### 2.2 当前文档形态的主要成本

机器狗 `tasks/active` 当前有 7 份 Markdown 任务文档，共约 1363 行，分别承载总体规划、接口台账、链路分析、复用评审、执行 backlog 和按日进度。它们能保留推演过程，但也出现了以下维护成本：

- 多份文件同时标为 active，旧文件的顶部状态与后续实际进度不一致。
- 一份文件声明自己是“接口评审唯一台账”，但部分最终口径又需要跳到复用评审、每日计划或长期契约文档确认。
- 已被推翻的“新增专属 identifier / Handler”方案仍留在 active 文档正文中，只能依赖顶部提示说明不再采用。
- 同一能力在 M、C、API、WS、A、B、F 等多套编号中重复出现，人工可以理解，但 AI 续跑时需要额外建立映射。
- 按日期追加的执行计划同时承载计划、实施结果和接口说明，文件会持续膨胀。

因此，流程化的重点不是再增加一套模板，而是建立**唯一权威位置、稳定能力编号、阶段门禁和状态回填规则**。

## 3. 推荐的任务包

每个功能在对应产品的 `tasks/active/` 下建立一个目录；评审通过并实施 Skill 后，再由治理校验决定是否正式采用该目录结构。

```text
tasks/active/<feature-id>/
|-- task.yaml                 机器可读状态、阶段、门禁、产物索引
|-- 01-impact-review.md       Step 1：范围与前后端对齐台账
|-- 02-api-contract.md        Step 2：人可读的接口/消息契约与决策
|-- 02-openapi.yaml           可选：可导入 Apifox 的 REST 契约
|-- 03-execution-backlog.md   Step 3：外部确认与可执行任务清单
`-- 04-integration-log.md     Step 4：联调矩阵、缺陷与提测证据
```

不复制原型大图、生产 payload、环境地址或敏感日志到任务包；只记录可访问来源、脱敏样本位置和证据摘要。

### 3.1 `task.yaml` 建议字段

```yaml
id: <feature-id>
title: <feature-title>
status: active
phase: impact_review
repositories: []
product: company/device-inspection-platform
prototype_sources: []
gates:
  G1_scope_confirmed: pending
  G2_contract_confirmed: pending
  G3_tasks_ready: pending
  G4_test_ready: pending
artifacts:
  impact_review: 01-impact-review.md
  api_contract: 02-api-contract.md
  execution_backlog: 03-execution-backlog.md
  integration_log: 04-integration-log.md
decisions: []
evidence: []
knowledge_update_assessment: deferred
sensitive_data_review: pending
```

`task.yaml` 只保存状态和导航，不复制四份文档的正文。任务归档时整体移动到 `tasks/archive/<feature-id>/`，并遵循现有 task metadata 契约补齐最终状态和 `archived_at`。

## 4. 四阶段工作流

### Step 1：影响范围与前后端梳理

目标是回答“原型中的每项能力会影响什么、当前是否已有、需要谁确认”，而不是直接承诺接口实现。

输入：

- 产品原型、截图、PDF、页面说明及可见交互状态。
- 本次允许读取的目标仓库及局部约束。
- 当前 REST、WebSocket、消息、缓存、数据表和上下游契约。
- 版本范围、明确非目标和交付时间边界。

AI 必须完成：

1. 按页面、弹窗、状态和交互建立原型证据清单，记录不可见、矛盾和缺失区域。
2. 把页面元素归类为输入、输出、查询、命令、导航、前端展示、计算、关联数据或未知。
3. 以“能力”为稳定编号，例如 `CAP-01`，后续接口、任务和验收都引用该编号，不再为同一能力建立多套互不映射的编号。
4. 核对现有代码与契约，并把每项判为：
   - `reuse`：同一业务语义可直接复用；
   - `change`：有相近入口但 DTO、状态、权限或数据源需调整；
   - `new`：当前没有对应业务能力；
   - `frontend_only`：纯展示或路由，不需要后端接口；
   - `upstream_dependency`：主要改动或前置在其他系统；
   - `out_of_scope`：已确认不在本期；
   - `unknown`：证据不足，不能排入实施承诺。
5. 对每个实时页面明确初始读取、增量刷新、断线重连和兜底策略。WebSocket 不能自动替代首屏 REST，也不能因为已有通道就判为业务可复用。
6. 生成产品、前端、当前后端、上游/下游各自需要确认的问题，并写明该问题阻塞哪个能力和需要取得什么证据。

Step 1 权威产物是 `01-impact-review.md`，至少包含：范围与非目标、原型追踪表、现状证据、接口影响矩阵、实时/兜底矩阵、跨服务责任、待确认清单和建议分批。

门禁 `G1_scope_confirmed`：产品范围、前端交互、复用/改造/新增结论和主要上下游责任已由相关人员确认。未通过时可以继续核实不依赖问题，但不能进入受影响契约的冻结。

### Step 2：初步接口定义与契约冻结

目标是把已确认影响范围变成前后端和上下游都能评审、实现、导入工具并用于验收的契约。

#### 推荐交付形态

采用“独立契约为评审权威，运行时代码为实施后的执行权威”：

- `02-api-contract.md` 是设计阶段必需产物，覆盖 REST、WebSocket、消息、成功语义、权限、数据来源和兼容性，适合前端、产品和上下游共同评审。
- REST 较多且需要导入 Apifox 时，增加 `02-openapi.yaml`，避免只靠 Markdown 手工二次录入。
- 进入实现后，以应用实际生成的 OpenAPI 为执行事实；验收时必须与已批准契约比对，差异需回写决策，不能让文档与 Controller 各自演化。

#### Controller/DTO 骨架的处理

不建议在所有项目中强制“先生成可访问但没有业务实现的 Controller”，因为这可能暴露伪接口、引入假成功或迫使代码层提前做未确认决策。

只有在以下条件都满足时，Step 2 才可增加 `controller-contract` 子模式：

1. `G2_contract_confirmed` 已通过，而不是用代码代替评审。
2. 目标仓库存在可复用的 API interface、Controller contract 或安全的骨架承载模式；不得为此凭空建立平行架构。
3. 骨架可以通过编译和 OpenAPI 生成，但不会把未实现能力暴露为正常成功接口。
4. 用户明确授权修改目标业务仓库。

若条件不满足，优先输出 OpenAPI 文件供 Apifox 导入；后续第一个代码任务再按批准契约创建 Controller、请求 DTO、响应 VO 和 Swagger/OpenAPI 注解。这比让一个独立 Markdown 永久与代码双写更可控。

#### 契约必须覆盖

- REST：method、path、权限/数据范围、请求、响应、分页/排序、错误语义、幂等与兼容性。
- WebSocket/事件：通道、业务码、信封、全量或增量、顺序/去重、项目隔离、首次读取、重连回拉和降级策略。
- 状态与命令：数据来源、刷新时效、未知/空值、允许状态、受理/发送/执行/失败/超时的区别。
- 跨服务：owner、identifier/topic/service、生产者、消费者、样本、发布顺序和失败责任。
- 数据：是否持久化、缓存、计算或关联查询；不能从 UI 展示字段直接推导数据库列。

门禁 `G2_contract_confirmed`：前端可按契约开始实现；后端不会因关键字段、成功语义、权限、实时策略或上下游责任未定而返工；仍未确认的能力明确移出本批次或保持 blocked。

### Step 3：任务清单、分批实施与结果回填

目标是形成可以逐个或按功能块交给 AI 执行的闭环任务，而不是只有粗粒度开发事项。

任务分三类：

- `EXT`：需要本人向产品、前端或上下游确认并带回证据的任务。
- `DEV`：前置已满足、可授权 AI 修改代码的任务。
- `INT`：需要指定环境、样本或协作方的联调与验收任务。

每个任务使用固定字段：

| 字段 | 要求 |
| --- | --- |
| ID / 能力 | 唯一任务 ID，并引用一个或多个 `CAP-xx`。 |
| 名称与目标 | 一句话说明可验收结果。 |
| 类型 / 负责人 | `EXT`、`DEV`、`INT` 与实际责任方。 |
| 前置与门禁 | 必须已完成的决定、契约、样本或上游能力。 |
| 上下文入口 | 本任务需要读取的原型区域、契约章节、代码入口、规则和测试；不要求重读全部历史文档。 |
| 范围 / 非目标 | 本次允许和禁止修改的仓库、模块、接口和数据。 |
| 执行步骤 | 按可独立验证的最小步骤编排。 |
| 预期结果 | 完成后系统或文档应具备的事实。 |
| 验收与验证 | 自动测试、OpenAPI 检查、样本、页面操作或实机证据。 |
| 状态与结果 | `ready/in_progress/blocked/verified/superseded`、实际结果、证据和剩余风险。 |

`DEV` 只有在所有前置为 `verified` 时才能标为 `ready`。`EXT` 未完成时，AI 可以执行不依赖它的核实或任务，不得把未确认语义实现为默认值。

用户可按以下方式驱动：

```text
执行 DEV-03
```

```text
按“机器狗状态首屏”功能块执行所有 ready 任务
```

每次实施后，AI 必须更新同一个 `03-execution-backlog.md`：实际改动、测试命令与结果、未验证项、知识更新判断和下一项；不再新建一份按日计划复制旧结论。

门禁 `G3_tasks_ready`：至少一个垂直切片的全部 `DEV` 任务已具备可执行输入，且每项有明确验收。阶段完成不是所有代码写完，而是任务体系已可持续执行和回填。

### Step 4：联调、提测与缺陷收口

目标是用契约与任务验收项组织联调证据，并将问题精确回溯到原型、契约、实现或环境。

`04-integration-log.md` 应维护一张矩阵：

| 场景 | 能力/契约 | 参与系统 | 输入与环境 | 期望 | 实际 | 证据 | 结论/缺陷 |
| --- | --- | --- | --- | --- | --- | --- | --- |

联调最少区分：

- 首屏 REST、实时更新、断线重连和兜底。
- 正常、空值、权限不足、重复、乱序、超时和上下游不可用。
- 同步 HTTP 响应、平台受理、消息投递、适配器发送和设备实际执行。
- 同项目、跨项目或不同角色的数据可见性。
- 发布顺序、观察点、回滚与旧版本兼容。

发现缺陷时先分类：

- 原型/需求遗漏：回到 Step 1，更新影响与确认项。
- 契约变化：回到 Step 2，记录决策并重新通过 `G2`。
- 实现缺陷：在 Step 3 新增或重开 `DEV` 任务。
- 环境/运行问题：建立 `INT` 任务；属于 Spring 后端事故时可使用现有诊断 Skill，但不能把环境问题直接改成业务 fallback。

门禁 `G4_test_ready`：本期能力的自动验证和必要联调证据齐全，所有未完成项已明确为阻塞、延期或非目标，提测范围、已知风险、发布顺序和回滚边界可追溯。

## 5. Skill 形态与路由

### 5.1 推荐：升级现有 Skill，不新增四个重叠 Skill

现有 `tu-scaffolding-spring-feature-from-prototype` 已覆盖原型提取、代码核实、设计预览、实现和验证。推荐保留名称和现有调用方式，在其内部增加生命周期路由，避免同时出现多个描述相近的自动触发 Skill。

建议支持以下模式，未显式指定时根据 `task.yaml` 和已有产物判断：

| 模式 | 触发语义 | 允许输出/动作 |
| --- | --- | --- |
| `impact` | “分析原型影响”“给前端梳理接口范围” | 创建或更新 Step 1；不改业务代码。 |
| `contract` | “根据确认结果定义接口”“出 Apifox 契约” | 创建或更新 Step 2；代码骨架需额外授权和条件检查。 |
| `plan` | “生成完整 task 清单” | 创建或更新 Step 3；不自动执行全部任务。 |
| `execute <task/block>` | “执行 DEV-03/某功能块” | 只实施 ready 且在授权范围内的任务并回填。 |
| `integrate` | “联调、提测、处理缺陷” | 执行 Step 4；按缺陷类型回流前置阶段。 |
| `status` | “现在到哪一步、还差什么” | 从任务包汇总门禁、阻塞、下一项和证据。 |

用户仍可只提供原型。若没有任务包，Skill 从 `impact` 开始；若已有任务包，Skill 不重复做完所有阶段，而是从当前门禁恢复。

### 5.2 建议的 Skill 资源

```text
tu-scaffolding-spring-feature-from-prototype/
|-- SKILL.md
|-- agents/openai.yaml
`-- references/
    |-- lifecycle-and-gates.md
    |-- prototype-extraction-checklist.md
    |-- impact-review-format.md
    |-- api-contract-format.md
    |-- execution-backlog-format.md
    |-- integration-verification-format.md
    `-- delivery-verification-checklist.md
```

`SKILL.md` 只保留模式识别、门禁、不变约束和引用路由；各阶段格式放入按需读取的 reference，避免每次加载全部模板。现有 `design-preview-format.md` 可拆入 impact 与 contract 两份，避免“范围评审”和“最终接口设计”在一次预览中混在一起。

本期不建议增加脚本。先用两个真实需求验证文件结构和门禁是否稳定；只有出现重复、确定性的状态检查或 OpenAPI 差异校验需求时，再增加脚本。

## 6. 关键规则

1. 原型证明页面意图，不证明权限、数据所有权、状态机、成功语义或数据库设计。
2. 当前代码证明现状，不证明新需求必须复用现有接口。
3. 技术通道可复用不等于业务契约可复用；Controller、WebSocket 通道、MQ Topic 和 service identifier 都需分别判断。
4. 同一能力始终使用 `CAP-xx`；接口、任务和联调记录引用它，不另建无法追踪的新编号体系。
5. 每个阶段只有一个权威产物；被推翻的方案移到决策历史或标为 superseded，不继续混在当前结论正文中。
6. 外部确认必须有结论与证据摘要；“开过会”或“同事说可以”不足以关闭影响公开契约的任务。
7. 接口文档与代码发生差异时必须显式决定：修改实现、修改契约或版本化；不得静默漂移。
8. 代码实施和外部发布仍需用户授权；Skill 的阶段状态不能扩大可操作仓库和外部系统范围。

## 7. 实施 P0 Skill 的建议任务

| ID | 任务 | 主要步骤 | 预期 | 验收 |

## 8. 方案验收标准

Skill 流程化完成后，应能满足以下场景：

1. 用户只提供原型和目标项目，AI 能输出有代码证据的影响范围文档，并明确需要用户对外确认的事项。
2. 用户带回前端/产品确认结果后，AI 只更新对应决定，输出可评审、可导入或可由 Controller 实现的接口契约。
3. 用户说“生成 task 清单”后，每个任务都有上下文入口、前置、步骤、预期、验收和责任人；外部任务与代码任务不会混为一类。
4. 用户说“执行 DEV-xx”或指定功能块后，AI 只执行 ready 任务，完成代码、验证和结果回填，不重复分析整个需求。
5. 用户换一个新会话说“继续这个功能”时，AI 能仅靠任务包判断当前阶段、权威结论、阻塞和下一步。
6. 联调缺陷能被分流到需求、契约、实现或环境，不通过临时 fallback 掩盖根因。
7. 任务完成后能给出提测范围、验证证据、剩余风险、发布/回滚边界，并按 P0 治理规则归档。
