| 故障事件 | `inspection_alarm_report` | `AlarmReportHandler` → `InspectionAlarmBusinessServiceImpl` | 事件载荷改为机器狗 `faults[]`，P1 在统一告警服务内按设备类型分支。 |

## 2. 代码核对后的关键影响

### 2.1 “最大属性类 → 专用对象”的正确落点

P1 的 `DeviceStatusPropertyHandler` 不是把原始 JSON 原样交给业务层：

```text
InspectionIotMessageConverter#convertAll
  → 生成 JsonNode payload
  → AbstractLoggingInspectionIotMessageHandler#handle
  → objectMapper.treeToValue(payload, DeviceStatusProperty.class)
  → DeviceStatusPropertyHandler#handlePayload
  → InspectionDeviceStatusBusinessServiceImpl#handle
```

`DeviceStatusProperty` 当前只定义机场/无人机字段，并标了 `@JsonIgnoreProperties(ignoreUnknown = true)`。所以机器狗字段若不先加入该类，会在 `treeToValue` 时被忽略；到了 Handler 或业务服务后，无法再从 `DeviceStatusProperty` 重新序列化出这些字段。

因此本轮可执行的建模方式应为：

```text
机器狗平铺 JSON
  → 扩展 DeviceStatusProperty（统一“最大入口 DTO”，含所有需要保留的机器狗字段）
  → 统一 Handler / 统一状态 Service 按 deviceId 的产品分类分支
  → objectMapper.convertValue(最大入口 DTO, RobotDogStatusProperty)
  → RobotDogStatusBusinessService（仅消费页面/业务真正需要的字段）
  → 机器狗快照、WS、REST
```

`RobotDogStatusProperty` 在这里是 **P1 内部专用对象**，不是新增上行 identifier、Consumer 或前端 API。它用于隔离机器狗状态规则，避免在机场/无人机 DTO 中直接写业务判断。

### 2.2 分支位置不能只凭 `productKey`

同事文档允许按“顶层 `deviceId` 对应产品或 `productKey=robot-dog`”分支。当前 P1 的可信设备分类来自：

```text
message.deviceId
  → ManagedDeviceQueryService#getDeviceById
  → IotDeviceQueryGateway#getDeviceById
  → P2 IoTDeviceApi#get
  → rpcDevice.categoryCode → DeviceDTO.categoryCode
```

建议将 `payload.productKey=robot-dog` 作为报文一致性校验，`message.deviceId` 查得的机器狗 `categoryCode` 作为最终分支依据。原因是 `productKey` 来自适配器上报，而 `categoryCode` 由物联网平台设备主数据管理。

当前 `DeviceStatusPropertyHandler` 本身没有设备查询依赖；若严格在 Handler 分支，就要向 iot 模块引入设备上下文解析能力。更小的改法是在 `InspectionDeviceStatusBusinessServiceImpl#handle` 的最前面完成设备类型判定，再委托机器狗专用业务服务。**分支最终放 Handler 还是 Service，仍需你和同事确认。** 无论放哪里，都必须做 `deviceId + deviceSn + categoryCode` 校验。

### 2.3 P2 异步语义已核实

P2 `IoTDeviceRpcApi#invokeDeviceService` 先看物模型服务的 `callType`：机器狗 TSL 为 `async` 时，P2 会直接下行并返回 `requestId`。现有 P1 `InspectionIotDeviceServiceImpl#invokeDeviceControl` / `#invokeConfigCommand` 默认传 `BLOCK`，但在当前 P2 实现中，服务为 async 时不会进入阻塞等待。

P1 仍应为机器狗调用显式传 `ASYNC`：语义清楚，也避免未来 TSL 被误改为 sync 时 P1 悄然阻塞。该调整不是设备“执行成功”的证据。

### 2.4 同事文档与 P1 当前实现的一个参数差异

同事文档要求机器狗适配器从 Gateway 的 `DeviceInfo.productKey/deviceName` 定位设备，TSL service 参数只使用 `command`、遥控或配置字段。

但 P1 当前 `AbstractInspectionIotCommand` 的 `targetDeviceSn` 虽然注释写“不进入物模型 params”，`InspectionIotDeviceServiceImpl#invoke` 实际仅移除了 `deviceId`、`timeoutSeconds`、`iotGatewayTag`，会把 `targetDeviceSn` 一并传入 `params`。P2 当前 RPC 未校验 service 的未知参数，适配器若忽略该字段可继续运行；但这与同事文档不完全一致，不能默认为长期契约。

## 4. P1 待办需要怎样调整

此前待办中“新增机器狗专属 identifier/Handler/命令回执”的部分不再适用，替换如下：

| 原方向 | 按同事文档调整后的方向 |
|---|---|
| 新增机器狗状态 identifier 与 `RobotDogStatusPropertyHandler` | 保留 `inspection_device_status_report` 与 `DeviceStatusPropertyHandler`；扩展最大 `DeviceStatusProperty`，在统一业务入口分支。 |
