## 1. 先说清楚：同一个 Topic 如何识别机器狗

`iot_business_event:DEFAULT_FLOW` 是巡检业务平台消费的**运输通道**，其中会混入其他产品的上行消息；不能、也不需要通过 Topic 区分机器狗。

机器狗需要经过两层识别，职责不可混淆：

| 层次 | 识别依据 | 用途 | 结论 |
|---|---|---|---|
| 消息路由 | `params.identifier` | 决定交给哪个消息 Handler | 必须由物联网平台/适配器按约定写入；P1 Router 只认该值。 |
| 设备类型校验 | `message.deviceId` 查询到的平台设备分类 `categoryCode`（机器狗分类） | 决定该 Handler 是否按机器狗业务处理及绑定项目 | 以平台设备主数据为准；上报的 `productKey=robot-dog` 只作一致性校验和日志，不作为授权或唯一可信来源。 |

因此，机器狗不需要独立 RocketMQ Topic。巡检业务平台需要新增“机器狗设备上下文解析”：通过 `deviceId`/`deviceSn` 定位独立机器狗设备，再校验其 `categoryCode` 是双方冻结的机器狗分类。不能复用当前 `InspectionDeviceContextService` 的机场—无人机父子设备假设，也不能把机器狗当作机场遥测处理。

### 1.1 当前代码中“设备类型分流”的实际入口

不要从全局搜索 `getDeviceById` 开始：它是通用查询方法，调用点很多。**实际排查/开发的起点是 P1 的统一上行 Consumer，真正新增的分流断点是机器狗专用 Handler。** 当前分支的类型校验才会在 Handler 内通过设备主数据的 `categoryCode` 完成。

建议按下列标志性入口逐个打开并打断点；`UP-01 → UP-05` 是一条机器狗状态消息在 P1 内必经的路径：

```text
P2 Data Rule 投递 iot_business_event:DEFAULT_FLOW
  ↓
[UP-01｜统一 MQ 入口]
InspectionIotUpstreamConsumer#handleMessage
  ↓  converter.convertAll(message).forEach(router::route)
[UP-02｜报文拆解 / 路由键提取]
InspectionIotMessageConverter#convertAll
  ├─ params.identifier → identifier
  └─ rawMessage.deviceId → InspectionIotMessage.deviceId
  ↓
[UP-03｜identifier 唯一路由]
InspectionIotMessageRouter#route
  ↓  identifier = <双方冻结的机器狗状态路由值>
[UP-04｜机器狗业务分流点：新增]
RobotDogStatusPropertyHandler#handle
  ↓
[UP-05｜机器狗设备上下文：新增]
RobotDogDeviceContextService#resolve(message.deviceId, payload.deviceSn)
  ├─ ManagedDeviceQueryService#getDeviceById
  ├─ IotDeviceQueryGateway#getDeviceById → IoTDeviceApi#get
  └─ rpcDevice.categoryCode → DeviceDTO.categoryCode
       ↓
     categoryCode == 机器狗 P2 分类编码 ? 进入机器狗业务 : 拒绝该消息
```

换句话说：`getDeviceById` 只是 **UP-05 内部依赖**；你需要重点跟进的是 `UP-01` 是否收到消息、`UP-03` 是否路由到 `UP-04`、以及 `UP-05` 是否把设备判定为机器狗。

对应代码入口与当前事实：

| 标识 | 先打开的位置 | 关键代码/字段 | 当前事实与机器狗改造 |
|---|---|---|---|

建议新增的机器狗上下文校验伪代码如下，便于你和同事确认责任边界：

```java
DeviceDTO device = deviceService.getDeviceById(message.getDeviceId())
    .orElseThrow(/* 机器狗设备不存在 */);

if (!ROBOT_DOG_P2_CATEGORY.equals(device.getCategoryCode())) {
    throw /* 消息 identifier 是机器狗，但设备分类不匹配 */;
}
if (!device.getDeviceSn().equals(payload.getDeviceSn())) {
    throw /* deviceId / deviceSn 不一致 */;
}
return device; // 后续用其 deviceId、项目/空间归属、权限上下文
```

其中 `ROBOT_DOG_P2_CATEGORY` 的具体值不能由巡检业务平台猜测，必须由同事在 B-01 中给出并写入物联网平台分类初始化 SQL。这个校验就是你要跟进的“按设备类型分流”最小代码入口。

## 2. 当前物模型已确认的事实

| 类别 | 当前物模型定义 | 对 P1 的含义 |
|---|---|---|
| 产品 | `productKey = robot-dog` | 物联网平台需给该产品/设备配置机器狗分类；巡检业务平台按分类分流。 |
| 属性 | 有 `identifier`、`reportType`、`deviceSn`、`productKey`，以及电池、模式、急停、补光、速度、里程、控制源、运控等平铺属性 | 适合作为机器狗 OSD/状态快照来源；应由专用 `RobotDogStatusProperty` 承接，不能绑定现有 DJI `DeviceStatusProperty`。 |
| 事件 | `inspection_alarm_report`、`inspection_control_notification_report` | 名称与当前 DJI 通用 Handler 相同，但当前事件 payload 和业务处理不兼容；见第 4 节，必须选择兼容方案。 |
| 服务 | `inspection_device_control`，`callType=async`；参数含 `command`、`lx`、`ly`、`rx`、`ry`、`bodyTurn`、`bodyHighLow` | 可复用 P1→物联网平台的服务调用主链路；P1 需新增机器狗命令 DTO/门面。异步返回不代表设备动作完成。 |
| 配置服务 | `inspection_config_command`，`callType=async` | 本版本若做传感器频率或摄像头码率控制，需要新增机器狗配置 DTO；不做则不接入 P1 页面。 |
| 坐标 | 仅有 `motionPositionX/Y/Z` 等本地运控位置 | **没有经纬度**。当前前端已确认需要最近经纬度地图点位，坐标转换责任与契约必须补齐，见第 6 节。 |

## 3. 推荐上行契约与路径图

### 3.1 状态属性：建议独立的机器狗路由 identifier

**当前已核实：** P1 的 `InspectionIotMessageConverter#convertAll` 固定从 MQ 原始报文读取 `params.identifier`，再由 `InspectionIotMessageRouter#route` 用该字符串选择 Handler。机器狗物模型也声明了一个属性，其属性名（TSL identifier）为 `identifier`，名称为“属性上报模型标识”。

**当前未核实/待冻结：** 该机器狗属性上报时的实际值。物模型未给出枚举、默认值或上行样本；P1 的 `InspectionIotIdentifiers` 也尚未存在机器狗状态常量。因此 `inspection_robot_dog_status_report` 是本方案提出的**推荐契约值**，不是从当前代码或物模型直接取得的事实。若同事确认采用，则再同步写入 P1 常量、机器狗 Handler 的 `identifier()` 和适配器/P2 上行报文。

该值不是把 `iot_business_event` 再分一个 Topic；它只是同一 Topic 中的一条消息路由键。

状态消息应使用当前 P1 Converter 已支持的属性上报形态：

```json
{
  "id": "...",
  "requestId": "...",
  "deviceId": 123,
  "method": "thing.property.post",
  "reportTime": "...",
  "params": {
    "identifier": "inspection_robot_dog_status_report",
    "reportType": "STATE",
    "deviceSn": "...",
    "productKey": "robot-dog",
    "robotMode": "general",
    "batteryPower1": 88.1,
    "softwareEmergencyStop": false
  }
}
```

P1 Converter 对 `thing.property.post` 会以 `params.identifier` 作为路由键，并把其余平铺字段组装为 Handler payload。因此 P1 的实现应为：

```text
inspection_robot_dog_status_report
  → RobotDogStatusPropertyHandler
  → 按 deviceId / deviceSn 解析独立机器狗设备并校验产品分类
  → 更新机器狗状态快照、最近位置、业务状态
  → 推送机器狗 OSD / businessStatus / 监控统计变化
```

`reportType` 可作为状态分包的内部字段，但不得代替 `params.identifier` 做 P1 路由。高频 IMU、JointState、运控原始数据不得默认全部经 P2 Data Rule 转给 P1；应由适配器/物联网平台按页面实际需要采样，只将 OSD、告警、控制权等业务数据投递 P1。

### 3.2 故障、控制权、命令回执：不要和 DJI payload 混用

当前物模型的两个事件 identifier 与现有 P1 Handler 同名，但当前 P1 行为如下：

- `inspection_alarm_report`：现有 Handler 解析 `AlarmReport.items`，HMS Service 又按 DJI `dock_tip_` / `fpv_tip_` 字典组装文案。
- `inspection_control_notification_report`：现有 Handler 只接受 `DRC_STATUS_NOTIFY`、`JOYSTICK_INVALID_NOTIFY`，并按机场上下文推送。

机器狗的 `faults[]`、`CONTROL_TAKEN` / `CONTROL_RELEASED` 不能直接进入这两条实现。P1 Router 同一个 identifier 只能注册一个 Handler，因此不能额外挂一个同名机器狗 Handler。

推荐在物模型发布前改为独立 identifier：

| 能力 | 当前物模型 | 推荐冻结值 | P1 落点 |
|---|---|---|---|
| 机器狗状态属性 | `identifier` 属性值尚未冻结 | `inspection_robot_dog_status_report` | 新 `RobotDogStatusPropertyHandler` |
| 机器狗故障事件 | `inspection_alarm_report` | `inspection_robot_dog_alarm_report` | 新 `RobotDogAlarmReportHandler` + 机器狗 HMS 映射 |
| 机器狗控制权通知 | `inspection_control_notification_report` | `inspection_robot_dog_control_notification_report` | 新 `RobotDogControlNotificationHandler` |
| 机器狗异步命令结果 | 当前物模型未定义 | `inspection_robot_dog_command_reply` | 新 `RobotDogCommandReplyHandler`，更新命令流水/WS |

如同事坚持复用现有两条事件 identifier，则他必须把 payload 完整适配为现有 `AlarmReport.items` 和 `ControlNotificationReport`，并由 P1 改造现有业务服务按设备分类分流。该方案会碰到 DJI HMS 文案、机场上下文和前端消息语义，风险与改动量更高；不建议作为首选。

### 3.3 上行全链路

```text
智元 SDK 回调 / 协议 1004、1005、1016、1017
  ↓  同事负责：字段转换、连接生命周期、设备身份
协议适配器 / 物联网网关
  ↓  IotDeviceMessage（deviceId、method、params.identifier、params/payload）
物联网平台
  ├─ 校验机器狗产品物模型、保存属性/运行态
  └─ Data Rule：仅将约定的机器狗状态、故障、控制权、命令回执转发
       ↓  RocketMQ iot_business_event:DEFAULT_FLOW
巡检业务平台 Consumer → Converter → identifier Router
  ↓
机器狗专用 Handler（状态 / 故障 / 控制权 / 命令回执）
  ↓
状态快照、最近位置、HMS、控制权会话、业务状态
  ↓
REST 首屏兜底 + WebSocket（OSD、businessStatus、告警、控制权、命令结果）
```

## 4. 下行对接方案

当前物模型已定义 `inspection_device_control`，这与 P1 当前 `InspectionIotCommandService#invokeDeviceControl` 使用的服务 identifier 一致。因此**下行传输主链路可复用**，但不能直接用现有 DJI DTO。

```text
前端机器狗页面
  ↓  机器狗 Controller / Service（P1 新增或改造）
设备分类、项目权限、机器狗控制权、命令白名单、审计、幂等
  ↓
RobotDogControlCommand（P1 新 DTO）
  ↓  identifier = inspection_device_control
IoTDeviceApi.invokeDeviceService
  ↓  校验机器狗产品的服务 TSL、设备 gateway 归属
物联网网关 / 协议适配器
  ↓  同事负责：1002 低频命令 / 1003 遥控报文 / SDK 调用
智元机器狗
  ↓
状态变化 + 命令回执事件 → 回到上行链路
```

### 4.1 P1 与同事的分工

| 范围 | 巡检业务平台（本人） | 物联网平台、网关、协议适配器、设备（同事） |
|---|---|---|
| 设备识别 | 用 `deviceId + deviceSn + 产品分类` 解析机器狗上下文，绑定项目与权限 | 创建/导入机器狗产品与设备，提供设备 ID、SN、产品分类、网关归属映射。 |
| 上行 | 新 DTO、Handler、快照、最近位置、HMS、WebSocket、前端 REST | 将 SDK 消息映射为冻结的 `method + identifier + payload`，配 P2 Data Rule，提供样本。 |
| 低频控制 | 命令白名单、控制权、审计、调用 `inspection_device_control`、前端文案 | 将 `command` 映射到协议 1002，给出 ACK/失败码/状态回报。 |
| 手动遥控 | 用户会话、权限、前端按键状态、断开时释放控制权 | 接收目标控制量，并在持有 SDK 连接的一侧以 50Hz 下发；超时必须自动归零。 |
| 急停 | 权限、操作审计、互斥校验、前端显示 | 映射急停/解除急停命令；上报软/硬急停真实状态。 |
| 异步结果 | 命令状态流水、WS 结果提示 | 每个异步服务回传 `requestId`、`command`、阶段、code/message、设备时间。 |

### 4.2 下行服务与命令冻结表

| 服务 | 当前物模型 | P1 处理建议 | 必须向同事确认 |
|---|---|---|---|
| 低频控制 | `inspection_device_control`，异步 | 新 `RobotDogControlCommand`，复用同一服务 identifier；不要扩写 DJI `DeviceControlCommand` 的飞行字段。 | 每个 `command` 到 1002/1003 的映射、参数是否必填、允许模式、设备 ACK 及错误码。 |
| 手动遥控 | `REMOTE_CONTROL + lx/ly/rx/ry/bodyTurn/bodyHighLow` | P1 只发送按键状态/目标向量及会话信息；不让 P1 HTTP 以 50Hz 轮询。 | 适配器 50Hz 定时、控制量 TTL、失联/浏览器断开归零、控制源切换、并发控制。 |
| 急停/解除急停 | `EMERGENCY_STOP` / `EMERGENCY_RECOVER`（物模型枚举） | 单独的机器狗接口和权限点；前端命令互斥；完成由真实状态确认。 | 软/硬急停区别、是否可解除硬急停、解除前置、指令 ACK/失败与状态上报。 |
| 模式/步态/速度/补光/充电 | 已列入 `command` 枚举 | P1 白名单校验后按异步命令发送。 | 每个枚举值是否真实支持 D1 Max、命令完成以哪一个 OSD 字段证明。 |

## 5. 巡检业务平台代码入口地图

## 8. 建议的联调顺序与验收样本

1. 同事先提供 B-01～B-04 的配置截图/导出和脱敏 JSON 样本；P1 以固定 `deviceId` 和 `deviceSn` 写 Handler 单测。
2. 先打通一条状态属性：状态消息进入 P1 后可识别机器狗、写快照、推 OSD 与独立 `businessStatus`。
3. 再打通一条故障“出现—重复—升级—恢复”事件，验证 HMS 数据和 WS。
4. 再打通控制权通知和一个低频动作（如站立），验证异步命令的“发送—受理/完成—OSD 状态变化”三段语义。
5. 最后打通手动控制、急停/解除急停、RTSP 与地图坐标；这些必须实机演练失败路径和断连保护。

每一步至少保留：P2 Data Rule 命中日志、RocketMQ 原消息、P1 Handler 日志、REST/WS 脱敏结果及设备实际状态证据。没有最后一项时，不能将异步命令标为“执行完成”。
